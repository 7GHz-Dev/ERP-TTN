# ระบบผู้ใช้และบทบาท

วันที่ 2026-11-26 · สถานะ: รออนุมัติ

## ทำไม

ตอนนี้ทุกคนที่ล็อกอินได้ทำได้ทุกอย่าง และต้องสร้างบัญชีผ่าน Supabase dashboard ด้วยอีเมล
ทีมต้องการบัญชีของแต่ละคน และแยกหน้าที่ตามบทบาท:

- **AON** จัดตารางงานคนขับ และประสานงาน Partner (รถร่วม)
- **SATANG** ตรวจสอบความพร้อมของคนขับ
- **admin** ดูแลระบบและผู้ใช้

## เป้าหมาย

1. มีบทบาท 3 แบบ และฐานข้อมูลเป็นตัวบังคับสิทธิ์ (RLS) ไม่ใช่แค่ซ่อนปุ่ม
2. ล็อกอินด้วยชื่อผู้ใช้ (`aon`, `satang`) ไม่ต้องมีอีเมล
3. admin จัดการผู้ใช้ได้จากในแอป: เพิ่ม, เปลี่ยนบทบาท, ตั้งรหัสผ่านใหม่, ปิด/เปิดบัญชี
4. หัวหน้าจอแสดงชื่อและบทบาทของคนที่ล็อกอิน และหน้าจอซ่อนหรือปิดปุ่มที่บทบาทนั้นใช้ไม่ได้

## ไม่ทำในรอบนี้

- รายการเช็กความพร้อมรายวัน (เช่น เช็กรถ/เอกสาร) สำหรับ SATANG ซึ่งเป็นฟีเจอร์ใหม่ คุยแยกภายหลัง
- แสดงว่า "ใครแก้งานล่าสุด" (`updated_by` มีอยู่แต่ไม่อัปเดตตอนแก้)
- หน้าแก้ข้อมูลคนขับ (ยังแก้ผ่าน Table Editor / สคริปต์นำเข้า)
- กำหนดสิทธิ์รายคนแบบละเอียด (สิทธิ์ผูกกับบทบาทเท่านั้น)

## ห้ามเกิด

- ผู้ใช้เดิม (บัญชี Gmail ของเจ้าของระบบ) ล็อกอินไม่ได้หลังอัปเดต
- คีย์ลับ (`SUPABASE_SECRET_KEY`) หลุดไปถึงเบราว์เซอร์
- ระบบไม่เหลือ admin (admin ลดบทบาทหรือปิดบัญชีตัวเอง)
- การรับแพลนจาก KOLA (`kola_receive_plan`) ใช้ไม่ได้

## ทางที่พิจารณา

| ทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| **1. RLS + หน้าจัดการผู้ใช้ในแอป** (เลือก) | admin ดูแลผู้ใช้เองได้, สิทธิ์บังคับที่ฐานข้อมูล | ต้องใส่ `SUPABASE_SECRET_KEY` ใน Vercel (ฝั่ง server เท่านั้น) |
| 2. RLS + สคริปต์ `add-user` ในเครื่อง | คีย์ลับอยู่แค่ในเครื่อง | เพิ่ม/รีเซ็ตผู้ใช้ได้เฉพาะเครื่องที่มีคีย์ |
| 3. ซ่อนปุ่มในหน้าจออย่างเดียว | ทำเร็ว | เลี่ยงได้ด้วยการเรียก API ตรง — ไม่ใช่การกันสิทธิ์จริง (ตัดทิ้ง) |

## บทบาทและสิทธิ์

รหัสบทบาทในฐานข้อมูล: `admin`, `planner` (AON), `readiness` (SATANG)

| | admin | planner | readiness |
|---|---|---|---|
| ดูแพลน / งาน / คนขับ / อัตรา | ✓ | ✓ | ✓ |
| นำเข้าแพลน จัดรถ แก้ราคา เปลี่ยนสถานะงาน ลบตู้ | ✓ | ✓ | – |
| ข้อความ LINE (ดู/คัดลอก) | ✓ | ✓ | ✓ (แค่อ่าน ไม่แก้ข้อมูล) |
| เพิ่มคนขับรถร่วม | ✓ | ✓ | – |
| แจ้ง/ลบวันไม่ว่าง | ✓ | ✓ | ✓ |
| แก้ข้อมูลคนขับ (ตาราง `drivers` update) | ✓ | ✓ | ✓ |
| แก้อัตราค่าขนส่ง (`rates`) | ✓ | ✓ | – |
| แก้ตัวเลือก (`lookups`) | ✓ | – | – |
| จัดการผู้ใช้ | ✓ | – | – |

(เจ้าของระบบเห็นตารางนี้แล้วและไม่ได้แก้ ถือเป็นค่าตั้งต้น)

## การออกแบบ

### ฐานข้อมูล (migration ใหม่ `20261126000000_user_roles.sql`)

- ตาราง `public.profiles`: `id uuid` (pk, อ้าง `auth.users` on delete cascade), `username text unique` (ตัวเล็ก a-z0-9._-),
  `display_name text`, `role text check in ('admin','planner','readiness')`, `active boolean default true`, `created_at`
- ฟังก์ชัน `public.my_role()` — `security definer`, `stable`, คืนบทบาทของ `auth.uid()` ถ้า `active` ไม่งั้นคืน null
- แทน policy "staff full access" ของแต่ละตารางด้วย policy ตามบทบาท:
  - select ทุกตาราง: `my_role() is not null`
  - `jobs`, `plans`, `rates`: insert/update/delete เมื่อ `my_role() in ('admin','planner')`
  - `drivers`: insert/delete `admin, planner`; update ทั้ง 3 บทบาท
  - `driver_unavailability`: insert/update/delete ทั้ง 3 บทบาท
  - `lookups`: เขียนได้เฉพาะ `admin`
  - `profiles`: select ทุกคนที่มีบทบาท (เพื่อแสดงชื่อ); ไม่มี policy เขียน — แก้ผ่าน server ด้วยคีย์ลับเท่านั้น
- ผู้ใช้ที่ไม่มีแถวใน `profiles` หรือ `active = false` = อ่าน/เขียนอะไรไม่ได้เลย
- migration สร้างแถว `profiles` ให้ผู้ใช้ทุกคนที่มีอยู่แล้วใน `auth.users` เป็น `admin`
  (ตอนนี้มี 1 บัญชี) username = ส่วนหน้า @ ของอีเมล
- `kola_receive_plan` เป็น `security definer` อยู่แล้ว ไม่โดน RLS — ไม่ต้องแก้

### ชื่อผู้ใช้กับอีเมล

Supabase Auth ต้องใช้อีเมล จึงแปลงชื่อผู้ใช้เป็นอีเมลภายใน `<username>@users.ttn.internal`
(ไม่มีใครส่งเมลถึง — สร้างผ่าน admin API ด้วย `email_confirm: true`)
หน้าล็อกอินรับได้ทั้งชื่อผู้ใช้และอีเมล: มี `@` = ใช้ตามที่พิมพ์, ไม่มี = แปลงเป็นอีเมลภายใน
บัญชี Gmail เดิมจึงยังล็อกอินด้วยอีเมลได้เหมือนเดิม
ถ้า Supabase ไม่รับโดเมน `.internal` ให้เปลี่ยนเป็นโดเมนอื่นที่ผ่านการตรวจรูปแบบ (เก็บไว้เป็นค่าคงที่ที่เดียว)
เหตุผลที่เลือก: ทีมไม่ต้องจำ/มีอีเมล และรีเซ็ตรหัสทำโดย admin อยู่แล้ว จึงไม่ต้องใช้อีเมลจริง

### คีย์ลับฝั่ง server

- `src/lib/supabase/admin.ts` มี `import "server-only"` สร้าง client ด้วย `SUPABASE_SECRET_KEY`
- ใช้ใน Server Actions ของหน้าจัดการผู้ใช้เท่านั้น ทุก action ตรวจก่อนว่าผู้เรียกเป็น admin ที่ active
  (อ่านจาก session ฝั่ง server ไม่เชื่อค่าจากเบราว์เซอร์)
- ตั้ง `SUPABASE_SECRET_KEY` ใน Vercel (ไม่มี `NEXT_PUBLIC_`) และแก้ README ที่เคยเขียนว่าห้าม

### หน้าจัดการผู้ใช้ `/users` (admin เท่านั้น)

- Server Component ตรวจบทบาท ไม่ใช่ admin → กลับไปหน้าแรก
- ตาราง: ชื่อผู้ใช้ · ชื่อที่แสดง · บทบาท · สถานะ · เข้าระบบล่าสุด
- ทำได้: เพิ่มผู้ใช้ (ชื่อผู้ใช้, ชื่อที่แสดง, บทบาท, รหัสผ่านเริ่มต้น), เปลี่ยนบทบาท, ตั้งรหัสผ่านใหม่, ปิด/เปิดบัญชี
- ปิดบัญชี = `profiles.active = false` + ban ใน Supabase Auth (session เดิมใช้ข้อมูลไม่ได้ทันทีเพราะ RLS)
- กันไม่ให้ admin ลดบทบาท/ปิดบัญชีตัวเอง และกันไม่ให้ admin คนสุดท้ายหายไป
- เข้าจากเมนูบัญชีที่หัวหน้าจอ (แสดงเฉพาะ admin)

### หน้าจอหลัก

- `page.tsx` อ่าน profile ฝั่ง server ส่ง `{ username, displayName, role }` ให้ `PlanBoard` แทน `userEmail`
- เมนูบัญชีแสดงชื่อที่แสดง + บทบาท, ลิงก์ "จัดการผู้ใช้" (admin), "เปลี่ยนรหัสผ่าน" (ทุกคน), ออกจากระบบ
- `readiness`: ซ่อนปุ่ม "นำเข้าแพลน", ปุ่มจัดรถอัตโนมัติ, ปุ่มเปลี่ยนสถานะ/เลือกคนขับ/แก้ราคาในแถวตู้, ปุ่มเพิ่มคนขับรถร่วม
  ยังดูทุกอย่างได้ และแจ้ง/ลบวันไม่ว่างได้
- ล็อกอินแล้วแต่ไม่มีบทบาท / ถูกปิด → แสดงข้อความ "บัญชียังไม่ได้รับสิทธิ์ ติดต่อผู้ดูแลระบบ" + ปุ่มออกจากระบบ
- โหมดสาธิต (`npm run demo`) = admin

### เปลี่ยนรหัสผ่านตัวเอง

Dialog ในเมนูบัญชี เรียก `supabase.auth.updateUser({ password })` จากเบราว์เซอร์ (ไม่ต้องใช้คีย์ลับ)

## ทดสอบ

- unit test: แปลงชื่อผู้ใช้ ↔ อีเมลภายใน, ตรวจรูปแบบชื่อผู้ใช้, ตารางสิทธิ์ (`can(role, action)`) ที่หน้าจอใช้
- ทดสอบ RLS จริงด้วยสคริปต์: ล็อกอินเป็นผู้ใช้ทดสอบแต่ละบทบาท แล้วลองเขียน `jobs` / `driver_unavailability` / `lookups`
  ยืนยันว่าได้/ไม่ได้ตามตาราง แล้วลบผู้ใช้ทดสอบ
- ลองล็อกอินด้วยบัญชี Gmail เดิมหลังรัน migration

## ขั้นตอนติดตั้ง (หลังพัฒนาเสร็จ)
